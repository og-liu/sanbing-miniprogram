# 项目目录结构说明

> 本文只回答一件事：**文件该放在哪、每个目录负责什么。**
> 云函数接口见《云函数接口文档.md》，视觉规范见《界面设计规范.md》，项目推进过程见《开发日志.md》；
> 测试命令、环境配置和上线步骤以根目录 README 为准。
>
> 维护规则：**目录结构发生变化时，先改本文，再改代码。**
> 不建议因为“文件多了”就随意新增目录；新增目录必须能在下面的职责表里找到唯一归属。
>
> 当前结构在 2026-11-11 完成云开发迁移和工程清理后定型：
> 页面只负责交互，服务层负责云端动作，工具层负责可复用的纯逻辑 / 平台能力，云函数是唯一可信数据入口。
> 已删除的 `server/`、`pages/logs/`、`utils/util.js`、个人中心资料弹层和 `docs/screenshots/`
> 不再属于当前结构；它们是历史阶段，详见《开发日志.md》。

## 二、页面层 `pages/`

### 1. 页面目录与职责

| 目录 | 职责 | 是否写云端数据 |
|---|---|---|
| `pages/index/` | 登录页：进入「我的」且未登录时打开；可「先逛逛」返回总览；非 tab | 登录时读取 |
| `pages/overview/` | 启动首页 / 总览 tab；未登录时说明账号数据需登录后读取 | 否 |
| `pages/visit/` | 拜访 tab，当前为空白状态；后续展示同盟成员列表 | 否 |
| `pages/alliance/` | 同盟 tab，当前为空白状态；后续承载创建 / 加入 / 管理 | 否 |
| `pages/wechat-profile/` | 用户主动编辑微信头像昵称（可选）；非 tab | 是（通过 `saveWechatProfile`） |
| `pages/init/` | 已登录但角色未初始化时填写游戏资料；已初始化自动回个人中心；非 tab | 是（通过 `saveGameProfile`） |
| `pages/game-profile-edit/` | 用户主动编辑游戏基础信息 / 总战力 / 核心属性；非 tab | 是（通过 `updateGameProfile`） |
| `pages/settings/` | 设置页：账号 / 微信资料编辑 / 注销账户 / 应用信息 / 本机退出登录；非 tab | 注销时写云端 |
| `pages/profile/` | 我的 / 个人中心；未登录直接转登录页；tab | 登录时读取 |

页面路由在 `app.json` 中显式登记，目前共 9 个，其中 4 个在 `tabBar.list`：
`overview / visit / alliance / profile`，这四个页面使用 `navigationStyle: "custom"` + `components/nav-bar/`。
`pages/overview/` 是启动首页；`pages/index/` 从「我的」未登录时进入，可「先逛逛」返回总览。
登录页使用自定义导航栏；微信资料 / 初始化 / 设置 / 角色编辑使用原生导航栏。

```text
启动 → /pages/overview/overview（不登录）
点击「我的」→ 未登录 ? /pages/index/index : /pages/profile/profile
登录页「先逛逛」→ /pages/overview/overview
微信登录成功 → 角色未初始化 ? /pages/init/init : /pages/profile/profile
```

tab 页面必须用 `wx.switchTab` 切换；非 tab 页面使用 `wx.reLaunch`。
统一通过 `utils/navigation.js` 的 `openRoute()` 判断，页面里不各自拼路由方法。

### 2. 一个页面四件套

```text
pages/<name>/
├── <name>.js       # 生命周期、data、事件处理、页面级编排
├── <name>.json     # 页面标题、usingComponents 等页面配置
├── <name>.wxml     # 结构与事件绑定
└── <name>.wxss     # 页面作用域样式
```

职责边界：

- `.js` 负责页面状态和交互编排；**不直接调用 `wx.cloud.database()` / `wx.cloud.uploadFile()`**。
- `.wxml` 只写结构和事件绑定，不在模板里做数据转换。
- `.wxss` 只写本页特有构图；颜色、字号、圆角、公共卡片 / 输入 / 按钮必须先引用 `app.wxss` 的 token 和公共类，规范见《界面设计规范》。
- `.json` 只写页面配置；页面标题使用中文，组件注册只在确实使用自定义组件时添加。
- 页面之间不共享页面实例、不互相 `require`；共享逻辑下沉到 `services/` 或 `utils/`。

### 3. 自定义组件

项目目前有两个自定义组件：

- `custom-tab-bar/`：四个 tab 的底部导航，使用 `"tabBar": { "custom": true }`；
- `components/nav-bar/`：四个 tab 页的自定义导航栏，用于替代原生导航栏并消除切页白色首帧。

页面内部仍保持 WXML 内联结构，不为了拆而拆；只有跨 tab 页复用的导航壳抽成组件。

### 4. tab 页与非 tab 页

- tab 页：`overview / visit / alliance / profile`，使用自定义导航栏和底部 tabBar。
- 非 tab 页：`index / wechat-profile / init`，使用原生导航栏，不出现底部导航。
- 页面切换：tab 页之间只用 `wx.switchTab`；流程页仍用 `wx.reLaunch`。

## 三、服务层 `services/`

| 文件 | 职责 | 对外主要接口 |
|---|---|---|
| `api.js` | 唯一的云函数调用封装；统一 `{ ok, data }` 响应、错误归一化、网络失败提示 | `call(action, data)`、`isAuthError(error)` |
| `auth.js` | 账号与资料动作的语义层；不保存 Session、不拼接用户 ID；本机退出只写本地标记 | `bootstrap()`、`saveGameProfile()`、`updateGameProfile()`、`saveWechatProfile()`、`resetProfile()`、`signOut()`、`isSignedOut()`、`clearSignedOut()`、`goToLogin()` |
| `onboarding.js` | 登录后的非强制分流、已登录标记与“稍后完善”本地偏好；不访问云端 | `getLoginRoute()`、`getAfterWechatProfileRoute()`、`has/mark/clearEnteredApp()`、`mark/clear/isWechatProfileSkipped()` |

**规矩**

- 只有 `services/api.js` 调用 `wx.cloud.callFunction`；页面和其他模块不得各自拼云函数名。
- 身份由云函数上下文提供，`services` 不接受页面传入的 OpenID、用户 ID 或 Session。
- `onboarding.js` 只做路由与本地 UI 偏好，不把“跳过”当成登录状态或身份凭证。
- `services` 可以依赖 `config/`，不依赖 `pages/` 或 `utils/display.js`；否则会把展示逻辑和业务动作耦合。
- 错误只向上抛统一的 `Error`（带 `code`），页面负责决定是 toast、重试还是回登录页。

## 四、工具层 `utils/`

| 文件 | 类型 | 职责 | 依赖 |
|---|---|---|---|
| `avatar.js` | 平台能力 | 读取本地头像、按需 `wx.compressImage`、转 Base64、执行 500KB 限制；供资料页保存使用 | `config/index.js`、`wx` 文件 / 压缩 API |
| `display.js` | 纯逻辑 | 将 `bootstrap` 返回的 bundle 映射为个人中心展示字段：微信资料、性别文案、格式化战力、组织状态、头像 URL | 无页面、无云 API |
| `validators.js` | 纯逻辑 | 游戏昵称、战力、性别、微信昵称的前端校验；提供即时错误反馈 | 无 |

**规矩**

- `display.js`、`validators.js` 不访问网络、数据库、`wx.cloud`，方便单测和复用。
- `avatar.js` 是明确标注的平台工具，允许使用 `wx` 的文件 / 压缩能力；不能把它的实现塞进 `display.js`。
- `utils/avatar.js` 的 500KB 限制是**前端体验层**；云函数仍必须独立校验大小和文件签名，
  不能因为前端已经检查过就信任请求。
- 前端校验与云函数校验有少量重复，这是**有意为之**：前端负责快速提示，服务端负责可信边界。
  不要把云函数的校验模块 require 到小程序端，也不要把前端校验当成安全校验。
- 新增通用纯函数先判断是否真的被两个以上模块使用；只被一页使用就留在该页，
  避免为了“看起来整齐”制造空工具。

## 五、云端 `cloudfunctions/sanbingAccount/`

### 1. 文件职责

| 文件 | 职责 |
|---|---|
| `index.js` | 云函数入口；初始化 `wx-server-sdk`；动作白名单 `bootstrap` / `saveGameProfile` / `saveWechatProfile`；通过 `getWXContext()` 识别用户；事务、上传、返回 bundle |
| `lib/validation.js` | 游戏昵称、总战力、性别、微信昵称、头像 Base64 等参数校验；服务端唯一权威 |
| `lib/avatar.js` | Base64 解码、大小检查、JPG/PNG/WebP 文件签名识别 |
| `lib/errors.js` | 统一的 `AppError`，保证错误码和错误消息可序列化返回 |
| `package.json` | `wx-server-sdk` 依赖与 Node 运行时约定 |

### 2. 云端规矩

1. **身份只来自 `cloud.getWXContext().OPENID`**，不接受客户端传入的用户 ID。
2. **所有业务集合读写都走云函数管理端**；客户端不直接读写 `sanbing_users` / `sanbing_game_profiles`，
   也不直接上传 `avatars/`。
3. 角色初始化必须用 `db.runTransaction` 同时写角色资料和 `profileInitialized`，避免半提交。
4. 云函数返回体不包含 OpenID、UnionID、session_key、头像 fileID；头像只返回短时临时 URL。
5. 云端是独立 Node 包，**不能 import 小程序端的 `utils/` 或 `services/`**；共同校验规则通过“同一语义、两处实现”保证，
   其中云端实现是最终信任边界。
6. 头像上传成功后再更新用户文档；替换头像时清理旧文件的逻辑必须保持，避免存储泄漏。
7. 云函数目录不进入小程序包，部署时必须单独上传；`project.config.json` 的 `cloudfunctionRoot` 指向 `cloudfunctions/`。
8. 当前运行时为 `Nodejs16.13`，超时 3 秒；正式运营前在控制台调到 20 秒（见 README 的部署说明）。

### 3. 当前数据集合

| 集合 | 内容 |
|---|---|
| `sanbing_users` | 平台账号、OpenID、微信昵称、头像 fileID、初始化标记、时间戳 |
| `sanbing_game_profiles` | 游戏昵称、总战力、性别、组织默认状态、初始化标记 |

账号与角色资料分表，以用户 ID 关联；详细字段、动作契约和错误码见 `docs/云函数接口文档.md`。

## 七、测试层 `tests/`

| 文件 | 覆盖对象 | 依赖方式 |
|---|---|---|
| `cloud-function.test.js` | 云函数纯逻辑：游戏昵称、战力、性别、微信昵称、Base64/大小/文件签名 | 直接 require `cloudfunctions/sanbingAccount/lib/*` |
| `onboarding.test.js` | 首登路由、已完善 / 已跳过 / 清除跳过后的分支 | mock `global.wx`，require `services/onboarding` |

**规矩**

- 测试只验证纯逻辑，不启动小程序页面；页面交互用开发者工具手工联调，联调结论记录在 `docs/开发日志.md`，运行命令见 README。
- 云函数测试直接测 lib 函数，不连接真实云数据库；真实云调用另做联调，避免单测依赖线上环境。
- 新增云函数纯函数优先加测试；新增页面路由分支也优先加 `onboarding.test.js` 风格的纯逻辑测试。
- 测试文件统一放在 `tests/`。这是一个小型项目的集中式约定，不采用和源文件同目录；
  如果测试数量明显增长，再评估按领域拆分。

当前测试：**2 个文件 / 8 个用例**。

```bash
node --test tests/cloud-function.test.js tests/onboarding.test.js
```

## 八、文档层 `docs/`

| 文件 | 作用 |
|---|---|
| `云函数接口文档.md` | 所有云函数的统一契约：调用方式、响应、身份、动作、数据、错误码和扩展清单；新云函数直接追加到本文件 |

| `项目目录结构说明.md` | 本文件：目录职责、放置规则、命名和结构红线 |

**规矩**

- `docs/` 只放文本文档，不放截图、构建产物或其他二进制资源；需要图片证据时放在外部文档系统，
  不重新引入 `docs/screenshots/`。

- `pages/` 不直接拼云函数名、不直接访问云数据库 / 存储。
- 云函数不能用前端传入的用户 ID 取代 `getWXContext()` 的身份。

## 十、新文件该放哪（判断流程）

按顺序问：

1. **它是一个页面吗？**
   → `pages/<kebab-name>/`，创建同名 `.js` / `.json` / `.wxml` / `.wxss`，在 `app.json` 注册。
2. **它是跨页面的云端动作或身份流程吗？**
   → `services/`。只有 `api.js` 负责底层云函数调用；业务动作放 `auth.js` 或新的语义化 service。
3. **它是纯展示映射或表单校验吗？**
   → `utils/`，优先保持无 `wx.cloud`、无页面依赖。
4. **它是文件读取、图片压缩等平台能力吗？**
   → `utils/`，文件名明确平台属性（如 `avatar.js`）。
5. **它是服务端可信逻辑吗？**
   → `cloudfunctions/sanbingAccount/`；公共校验进 `lib/`，动作入口留在 `index.js`。
6. **它是测试吗？**
   → `tests/`，与现有测试命名保持一致。
7. **它是文档吗？**
   → `docs/`，只写文本；同步更新 README 或相关文档引用。
8. **它是本地生成物 / IDE 配置吗？**
   → 不放进源码结构；确保在 `.gitignore` 中忽略。

**新增目录的门槛**：必须有至少两个以上文件，且职责无法归入现有目录；不能只为一个文件建新层。
新增目录时必须先在本文件登记，再在代码中使用。

## 十一、命名约定

| 对象 | 规则 | 示例 |
|---|---|---|
| 页面目录 | `kebab-case`，与页面名一致 | `pages/wechat-profile/` |
| 页面四件套 | 目录同名 + `.js` / `.json` / `.wxml` / `.wxss` | `pages/init/init.js` |
| 服务文件 | 小写、语义明确的单词 | `services/auth.js`、`services/onboarding.js` |
| 工具文件 | 小写、职责单一的单词 | `utils/avatar.js`、`utils/validators.js` |
| 云函数目录 | 已部署的 `sanbingAccount` 固定不改名；新增函数用 camelCase | `cloudfunctions/sanbingAccount/` |
| 云函数动作 | camelCase，作为 `action` 字符串 | `bootstrap`、`saveGameProfile`、`saveWechatProfile` |
| 数据库集合 | `sanbing_` 前缀 + 小写下划线 | `sanbing_users`、`sanbing_game_profiles` |
| 云存储路径 | `avatars/<publicId>/<timestamp>-<random>.<ext>` | `avatars/.../179...jpg` |
| 测试文件 | 被测领域 + `.test.js` | `onboarding.test.js` |
| 文档 | 名称清晰，长期维护的接口 / 设计文档使用中文主名 | `云函数接口文档.md`、`界面设计规范.md`、`开发日志.md` |
| 页面事件处理器 | camelCase，动词开头 | `onSave`、`onSkip`、`onChooseAvatar` |
| JS 模块 | CommonJS `require`；项目内用相对路径，无路径别名 | `require('../../services/auth')` |

**关于路径别名**：微信小程序原生和云函数 Node 环境都没有统一配置 `@/` 别名的必要；
当前统一使用相对路径。跨目录移动文件时必须同步改 `require`，这是本项目的明确取舍。

**代码风格**：2 空格缩进、单引号、无分号（沿用现有文件）；页面方法内保持早返回，
错误统一交给页面决定展示方式。没有 ESLint 配置，提交前至少执行 JS 语法检查。

## 十二、结构红线

以下情况视为结构问题，不是风格偏好：

1. **在小程序端直接调用 `wx.cloud.database()` 或 `wx.cloud.uploadFile()`** 读写业务数据。
2. **绕过 `services/api.js` 直接拼 `wx.cloud.callFunction({ name: ... })`**。
3. **把前端传入的 OpenID / 用户 ID 当作可信身份**，或重新引入自建 Session、`wx.login` 换取 Session 的旧链路。
4. **云函数返回 OpenID、UnionID、session_key、头像 fileID**，或在日志里打印这些值。
5. **云函数直接 import 小程序端 `utils/` / `services/`**，或小程序端 import 云函数代码。
6. **在 `services/` / `utils/` 中 import `pages/`**，或在 `app.js` 里写业务逻辑。
7. **为同一功能保留两套微信资料编辑 UI**（个人中心弹层 + 独立页），或复制一份保存逻辑。
8. **新增页面不注册到 `app.json`**，或在 `app.json` 注册不存在的页面。
9. **把 `.idea/`、`project.private.config.json`、`cloudfunctions/**/node_modules/` 提交进仓库**。
10. **在 `docs/` 中放截图、构建产物或其他二进制资源**；文档只保留文本。
11. **在 `.js` 中直接操作页面 DOM / 依赖页面实例跨页传递状态**（小程序端无 DOM，跨页只走路由和云端数据）。
12. **把“稍后完善”的本地跳过标记当成登录态 / 鉴权依据**。
